# Integration architecture
- The data layer is dual-mode: `admin()` in `src/lib/auth.server.ts` returns the direct-PostgreSQL adapter (`src/lib/pg.server.ts`) when `DATABASE_URL` is set, otherwise the cloud Supabase client. All privileged DB access must go through `admin()`/`dbQuery`, never a direct Supabase client import, so both modes stay in sync.
- Role AI uses shared role-scope helpers, current JD drafts and scoped work assessments; generated profile fields require explicit save and fit summaries cannot equate filled seats with capability.
- Offer terms and sequential approvals use thin app-owned authenticated server functions with dynamically imported server-only helpers and service-only transactional SQL; immutable versioned events prevent concurrent approvals and partial onboarding in both database modes.
- Presence reads both allowlisted tables through one privileged aggregate SQL view and rejects mismatched content versions across pages/endpoints; separate reads and timestamp cutoffs cannot guarantee complete syncs.- Talent pool uses dedicated app-authenticated server functions (Owner/HRD/HR/Recruiter) on a service-only table; AI matches only open positions in the caller's scope and CVs are stored as extracted text, not files, so both database modes work.
- Talent pool stores actual TeamTailor applied job titles as text[] from each candidate's application relationships, separate from AI matches; this keeps supplier history intact and avoids jsonb-array encoding in on-prem mode.
- Talent AI analysis requires readable CV text (PDF/.docx, TeamTailor fetched with one retry) and drops extracted schools/employers not found in the CV; profile-only input caused invented facts.
- Datalink offer approval is an env-configured adapter (DATALINK_* vars) storing request id/status on offer_requests; IT owns the API contract, so nothing is hard-coded.
